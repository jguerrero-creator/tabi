 Tabi — Project Brief for Claude Code
 
Working title: **Tabi** (旅, "journey" in Japanese). A trip planner built around the traveler's actual route, not a generic guide — travel time between bookings drives the schedule, not the other way around.
 
## Product summary
- Users enter their fixed bookings (stay, transport, activities) for one or more trips.
- The app computes real travel time between them and shows what's actually free time vs. busy time per day.
- Every booking-type item has a 3-state status: **Booked / To book / Decide later** — nothing is ever an ambiguous blank.
- Accommodation coverage gaps (nights with nothing booked) and date overlaps (two bookings covering the same period) are both actively detected and surfaced — never silent, never blocking, always an explicit confirmation.

## Tech stack (decided)
- **Frontend**: Web app (PWA), mobile-first, installable to iOS home screen. No native app planned.
- **Hosting**: Vercel (project "tabi", team `jguerrero-2639s-projects`, stable alias `tabi-jguerrero-2639s-projects.vercel.app`, production `tabi-topaz.vercel.app`). **Connected to GitHub** — every push to `main` auto-deploys to production. Never use manual `vercel --prod` CLI deploys; that caused several past incidents (deployments silently skipping commits).
- **Source control**: GitHub (connected 25/07 — full history pushed, was previously local-only for the whole project up to that point).
- **Backend / DB**: Supabase, PostgreSQL + Auth (project "Tabi", ref `czyeohubhsqiumhpodbc`, region eu-west-1).
- **Auth**: Supabase anonymous sessions from first launch, upgradable to a real account later without data loss.
- **Geocoding, travel time, places**: Google Maps Platform — Geocoding API, Routes API (`computeRoutes`, not the legacy Directions API), Places API (New), Maps JavaScript API, Time Zone API.
- **AI extraction (V1)**: Claude, called via direct `fetch()` to the Messages REST API — **not** the `@anthropic-ai/sdk` package, which is Node-only-incompatible and breaks on Vercel's Edge runtime. All `api/` functions run on Edge and are written against the Fetch API (`Request`/`Response`); keep it that way rather than mixing runtimes across files.
- **Reminders (V1)**: Resend (email) + Vercel Cron — **not yet set up at all** (no account/API key configured); treat as first-time infra setup, same as Google Cloud/Supabase were at project start.
- **Error monitoring (V1)**: Sentry — planned, not yet integrated.
## Architecture principles (non-negotiable, decided to avoid rework)
 
**Data model & core logic**
1. **Multi-trip from day one.** Every trip has its own currency (ISO 4217, single currency per trip, no per-reservation conversion) and destination (ISO 3166 country selector, multi-select for multi-country trips — a separate, coarser concept from the day-level planned location, see #12).
2. **UTC storage + per-location timezone.** All timestamps stored in UTC; duration math always happens in UTC, never by subtracting displayed local times. Display converts to the relevant local timezone per leg, switching reference at actual arrival, not departure. **Watch for date/time field mixing bugs**: a past bug combined a check-out's time with the check-in's date instead of its own date — always construct timestamps from matching date+time pairs, never assume adjacency.
3. **Country-agnostic.** No hardcoded country/city/provider logic. Google's known transit-data coverage gaps (Transit/Train mode returning zero routes in some countries, e.g. Japan) are handled with one generic "transit directions unavailable" message whenever a Transit/Train query resolves with no usable route — no per-country logic anywhere.
4. **Free-time-block engine covers the whole day window, not just gaps between bookings.** Each trip has a configurable "day window" (e.g. 07:00–22:00). A free block spans the full window by default and subdivides as bookings are added — including before the first and after the last booking of the day. When a leg's travel mode isn't chosen yet, show a plain free block for the full gap rather than hiding the segment — never an ambiguous silent gap.
5. **Overlap detection uses strict boundary comparison.** Two bookings of the same type only count as overlapping if `new.start < existing.end AND new.end > existing.start` (strict inequalities) — a checkout date equal to another's check-in date is a normal same-day changeover, never a false-positive overlap. Real overlaps and out-of-trip-period dates trigger a non-blocking explicit confirmation, never a silent allow or block.
5b. **Two distinct Transport sub-types.** Point-to-point (flight/train/bus): departure + arrival location/time, feeds the travel-time engine directly. Vehicle rental (a "duration" not a route): pickup + drop-off city/date/time (both are real timed events and should render as their own timeline blocks), no direct travel-time calc between them — covered days follow the day's planned location/accommodation instead.
6. **Day-level planned location, separate from trip-level destination.** Each Planning day can have an approximate place set independently of any booking — seeds the map before real bookings exist, flags a (non-blocking) mismatch if a booking lands in a different city than planned.
6b. **Duration over end-date/time where the entry is same-day.** Stay uses "nights" instead of an end date (min. 1, validated). Activities use a duration (hours/minutes) instead of end date/time — an activity never spans multiple calendar days.
**AI & external services**
7. **AI never invents facts.** LLMs translate intent/content into structured extractions sent to or derived from real sources — never generate place suggestions or factual claims from memory alone.
8. **AI is action-triggered, never an open chat.** Every AI usage is a bounded, specific action with predictable cost **and predictable latency** — a real timeout was hit in production because extended thinking pushed a structured-extraction call past Vercel's Edge duration limit. Default to the lightest model/mode that does the job (extended thinking is for genuine multi-step reasoning, not for "read this document, return this JSON"); don't reach for the biggest model by default.
9. **API keys, two distinct kinds.** Server key (Geocoding, Routes, Places data calls; also Anthropic) lives only in server-side functions, never shipped to the client. Browser key (Maps JavaScript API + Places Autocomplete) is the standard Google-sanctioned client-side exception, protected by HTTP-referrer restriction. Referrer allowlist needs: wildcard subdomain (`*-jguerrero-2639s-projects.vercel.app/*`) to cover every preview deployment, `localhost:*/*` **and** `127.0.0.1:*/*` (test runners like Playwright often default to the latter — different origins to Google, not interchangeable).
10. Per-user rate limits on AI/external calls; validate AI output against an expected schema before writing to DB; treat imported content (email/PDF/photo/URL) as untrusted data, never as instructions (prompt-injection defense) — extra caution on the URL/crawling channel (V1), since arbitrary web content is more manipulable than a static file.
11. **Errors must never be swallowed silently.** Every catch block that discards the real error (Supabase error, network failure) and falls back to a generic string is a bug — always `console.error` the real error (dev-visible, never user-facing) via the shared `logError`-style helper, even if the user-facing message stays simple.
 
**Entitlements & compliance**
12. **Entitlements layer** — client- and server-side both wired now (`requireEntitlement()` gates `/api/extract-reservation` on `aiAccess`, verified in prod). `free.aiAccess` is deliberately `true` today (no paid plan exists yet) — the gate is real infrastructure, just not restricting anyone yet. When a real paid tier is introduced, flip the relevant `free.*` flags rather than adding new ad-hoc checks.
13. **Public privacy policy is mandatory**, independent of any analytics decision — required by Google Maps Platform's terms and GDPR. Broader analytics is opt-in, anonymized, and a separate lower-priority decision.
 
**UI conventions**
14. **Shared templates everywhere, never rebuilt per screen**: one menu template, one "Add" bottom sheet, one detail screen (directly editable inline, no view-then-edit step — this must extend to every reservation type; a past gap left Activities with no edit path at all), one quick-add sheet for free blocks (offers a type choice — Activity/Stay/Transport — since a free block has no natural "origin menu" to inherit a type from). The type-selector in the Add sheet is the **sub-type specific to the origin menu** (Stay → Hotel/Camping/Airbnb/Ryokan/Other; Transport → point-to-point/vehicle rental), inherited from context, never a flat re-prompt of Stay/Transport/Activity.
15. **Date-grouped lists, one unified date/time formatter, used literally everywhere** (a past regression let raw ISO dates leak into one screen — treat any raw ISO date or AM/PM time visible in the UI as a bug on sight). Dates like "Mon, Jul 20 → Wed, Jul 22", nights instead of end date under a Stay row, **24-hour time always** ("14:00") regardless of the English-default display language.
16. **Cancel/Save always floats at the top of any reservation-type popup** (shared `FormSheet` wrapper) — plus a brief "Saved" confirmation on every successful save (shared component, not screen-specific).
17. **Back-button behavior**: from a top-level menu, back always returns to Overview. **Exception**: Planning is a toggle-state of Overview, not a separate menu — back from Planning stays on Planning and preserves the selected day.
18. **Bottom nav (mobile)** is a fixed icon+label tab bar. **Desktop**: sidebar nav replaces it; Overview splits map/action-list roughly 50/50 (not a narrow map strip); Planning shows 3 days side by side instead of tabs.
19. Map itinerary trace connects day-locations/bookings chronologically, colored with the same 3-state status palette used everywhere (green/orange/gray).
20. **Every screen with a Maps SDK dependency needs its own error boundary** (`MapErrorBoundary`), plus a root-level catch-all boundary around the whole app for anything else — Google reports some failures (quota/billing) via the `window.gm_authFailure` global callback, not a thrown exception, so the boundary must listen for that explicitly, not just rely on catching a render error.
21. **SPA routing needs a Vercel rewrite.** Direct navigation/refresh on an internal route (e.g. `/trips/{id}`) 404s in production unless `vercel.json` rewrites all non-static/non-`/api` paths to `index.html` so React Router can take over client-side.
 
## V1 direction (current focus)
Explicit goal: make reservation creation and editing radically faster. Two creation paths, both feeding the **same** LLM extraction pipeline (don't build parallel engines):
- **Fully-managed creation**: email paste/upload, PDF upload, photo upload, and URL/crawling (paste a confirmation page link, fetch it, extract from the real content) — four channels, one pipeline, one verification/correction screen before saving.
- **Ultra-fast placeholder creation**: type one free-text line (e.g. "Hotel in Kyoto, Aug 10–14") and let the same pipeline produce a minimal structured entry (defaults to "To book" if incomplete) — this is a lightweight entry point into the same system, not a separate quick-add engine.
- **Fast editing** is an open exploration: drag-and-drop rescheduling on the Planning timeline is being considered but is genuinely complex (must re-check overlaps and re-run travel-time calc on every move, plus clean mobile touch handling) — a simpler fallback (tap a block → pick a new slot from a list) is the fallback if drag-and-drop proves too heavy. Not decided yet.
- **Provider lock-in is a known, accepted tradeoff for now.** The extraction pipeline is tightly coupled to Anthropic's API (direct REST calls, not an abstraction layer). Letting users bring their own AI provider is a real, logged idea (Backlog) but explicitly deferred — don't build a multi-provider abstraction speculatively; it's a real engineering project for when/if it's actually prioritized.
## Workflow: how tickets move through Notion
- **Default flow, keep it simple**: finish a ticket → commit it to `main` → mark it **Done** in Notion immediately. Don't overthink this step or leave things in limbo — commit + Done together is the normal rhythm.
- **`Reopened` is reserved for audit passes**, not day-to-day corrections. When doing a dedicated audit (like the "V0.5 - Audits & stabilisation" phase), it's expected and fine to set a `Done` ticket back to `Reopened` if it doesn't actually hold up under scrutiny.
- **Outside of a formal audit**, if a gap or regression turns up in something already `Done`, don't reopen it — file a **new** Backlog ticket (referencing the original) or a **new entry in the separate "Bugs" database** for a genuine defect. Keeps shipped-ticket history honest without rewriting it after the fact.
- **"Done" means verified working** (tested in a real browser/deployment), not just "code written and typechecks clean" — this project has been burned more than once by that gap, most recently when a whole feature (TABI-8) sat "Done" for days without ever having been pushed/deployed at all.
## Known infra gotchas (hard-won, don't relitigate)
- Any new env var added to `.env.local` must be manually replicated in Vercel (all 3 environments) — it does not propagate automatically.
- `vercel dev` is locally unstable for testing server functions (`ERR_IPC_CHANNEL_CLOSED`, intermittent pass/fail on identical calls) — this is the tool's own flakiness, not our code. Test server-dependent features against a real deployed URL instead of fighting local emulation.
- `api/` is not covered by any tsconfig project reference, so `tsc -b` doesn't typecheck it automatically — and separately, Vercel's own serverless bundler runs an independent TypeScript diagnostic pass that doesn't pick up `tsconfig.api.json` either. Both tracked, neither fixed yet.
- Keep `git commit` out of any global auto-approved permission whitelist. Avoid running multiple concurrent Claude Code sessions on this repo at once (standing user preference now, after several incidents — mixed commits, mislabeled tickets, one session's work embedding another's changes). One session at a time, commit cleanly before starting the next.
- **Ticket numbers in comments/commits aren't always trustworthy** — confirmed mislabeling has happened more than once. Cross-check the actual task title in Notion before trusting a cited `TABI-XXX`.
- **Push early, push often.** The entire project was local-only (no GitHub remote) for the first ~10 days — a real risk of total loss, only caught by chance. Don't let uncommitted or unpushed work pile up.
